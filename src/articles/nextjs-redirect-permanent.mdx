프로젝트를 개발하던 중 로그인 뒤 이동할 워크스페이스를 바꾸는 작업을 했습니다. 리다이렉트 목적지는 A에서 B로 수정했지만 브라우저는 계속 이전 목적지 A로 이동했습니다.

코드는 새 목적지를 가리키는데 결과만 바뀌지 않았습니다. 이 현상을 따라가면서 영구 리다이렉트는 주소를 한 번 옮기는 데서 끝나지 않고, 브라우저가 다음 이동에도 그 결정을 재사용할 수 있다는 사실을 알게 됐습니다.

`308 Permanent`와 목적지 `A`를 선택한 채 요청을 보내보세요. 브라우저 캐시에 `/login → /workspaces/a`가 남습니다. 이제 서버 목적지만 `B`로 바꾸고 다시 요청하세요. 서버는 B를 가리키지만 결과는 여전히 A입니다.

## 서버보다 캐시가 먼저 움직인다

설정을 따라가 보니 서버는 `308 Permanent Redirect`를 응답하고 있었습니다. 308은 이 이동이 영구적이라는 뜻이며, 브라우저는 출발 주소와 목적지를 함께 기억할 수 있습니다.

```http
HTTP/1.1 308 Permanent Redirect
Location: /workspaces/a
```

다음에 `/login`을 방문하면 브라우저는 서버에 묻기 전에 저장한 목적지를 사용할 수 있습니다. 서버가 새 요청을 받지 못하므로 코드를 B로 바꿔도 이전 목적지 A로 이동합니다.

문제는 목적지가 로그인할 때마다 달라지는 값이었다는 점입니다. 같은 `/login`에서도 사용자가 선택한 워크스페이스에 따라 A나 B로 보내야 합니다. 변할 수 있는 관계를 영구적인 관계로 응답한 것이 원인이었습니다.

## 영구와 임시는 다음 요청에서 갈린다

307과 308은 모두 요청의 메서드와 본문을 유지한 채 다른 주소로 보냅니다. 여기서 중요한 차이는 다음 요청입니다.

- `308 Permanent Redirect`는 같은 이동을 다시 사용할 수 있는 영구 응답입니다.
- `307 Temporary Redirect`는 이번 요청에만 적용하는 임시 응답입니다. 다음 요청에서는 서버가 목적지를 다시 결정합니다.

목적지가 사용자나 세션에 따라 달라진다면 브라우저가 이전 결정을 재사용해서는 안 됩니다.

## 변하는 목적지는 임시로 보낸다

문제가 된 Next.js 코드에서는 `permanent: true`가 308 응답을 만들고 있었습니다.

```ts
return {
  redirect: {
    destination: `/workspaces/${workspaceId}`,
    permanent: true,
  },
};
```

로그인 뒤처럼 목적지가 매번 계산되는 이동에는 `permanent: false`를 사용합니다. 응답은 307이 되고, 다음 방문에서도 서버가 현재 목적지를 결정합니다.

```ts
return {
  redirect: {
    destination: `/workspaces/${workspaceId}`,
    permanent: false,
  },
};
```

## 코드를 고친 뒤에는 캐시도 지운다

이미 저장된 308은 서버 코드를 바꿔도 사라지지 않습니다. 데모에서 307로 바꾼 뒤 바로 요청해보세요. 캐시가 남아 있는 동안에는 여전히 A로 이동합니다.

`캐시 지우기`를 누르고 다시 요청하면 서버가 선택한 B로 이동합니다. 이후 목적지를 A와 B 사이에서 바꿔보세요. 307에서는 매번 현재 서버 설정을 따릅니다.

이 일을 겪고 나서 `permanent`를 단순한 상태 코드 선택으로 보지 않게 됐습니다. 영구 리다이렉트는 이번 이동뿐 아니라 다음 요청에서 서버를 다시 거칠지까지 바꿉니다. 주소의 관계가 앞으로도 바뀌지 않을 때만 사용하고, 잘못된 308을 이미 응답했다면 코드와 함께 브라우저 캐시도 바로잡아야 합니다.
